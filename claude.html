Claude often ran out of room before handing in the work.

Claude Opus 5.5 (default settings) finished and handed in a file on 144 of 220 tasks. The biggest gap was turning a lot of work into a delivered file within fixed limits.

In plain English

Every task had the same limits: at most 14 rounds of work, 24 actions such as web searches, and a cap on how much text the model could write. Claude often spent its allowance researching and planning, then ran out before saving the requested file. When Claude did deliver, its files often scored well. The fix we suggest is training examples that teach the model to save a basic version of the file early and then improve it.

Why this dataset is worth buying, for evaluation and for training

As an evaluation: it tests finishing real work under real limits.

  • It catches a failure that answer-only tests can't. The 62 cut-off tasks show up only because each task requires a saved file within fixed limits. A test that grades the text of an answer would not reveal them.
  • The headline check is objective and cheap. Whether a file exists and opens in the requested format needs no AI judge, so it can be rerun on every model version and limit setting.
  • It separates "can't" from "ran out of room". Rerunning the same tasks with more room is a built-in experiment for measuring how budget-efficient each model version is.

For training: it shows exactly what to teach.

  • Delivery is the biggest, cheapest gap. 76 of 220 tasks ended without a usable file, versus 9 for GPT. However good the unfinished work was, none of it reached the customer.
  • The work was mostly there. With more room, 53 of the 62 cut-off tasks produced a file, so the skill to learn is budgeting: deliver first, then improve.
  • Quality is the second step. On tasks where both delivered, our 12-item Claude draft ledger shows quantitative errors (4) and misread inputs (3), such as a wrong legal identifier in a case file.

This is not just about file types Claude can't handle. Even on the 205 tasks with no known file-type limitation, Claude finished 150 versus GPT's 200.

Follow-up: what happens with more room?

We re-ran the 62 cut-off tasks from scratch with larger limits: up to 32,000 tokens per reply (was 10,000), 150,000 per task (was 50,000), 28 rounds (was 14) and 48 actions (was 24).

Result: 54 finished, and 53 of those included a file. Four were still cut off and four hit server errors. This suggests the limits explain much of the gap. However, several settings changed at once, and the retry files have not been graded, so this does not replace the main results.

Where Claude's work was stronger

Where both judges agreed, Claude did better on 29 tasks and GPT on 17. Examples include a surveillance report that tied photo evidence to each timeline entry, and the warehouse safety procedure in the worked example. On most tasks the judges could not separate the two models, so this is not an overall ranking.

Proposed dataset: deliver first, then improve

A training dataset proposal describes new examples that could teach the model to fix this weakness. This is a draft specification; sizes are starting points to test, not commitments.

Task mixLong, multi-step professional assignments that need research, input files and a saved file: financial models, reports, presentations and spreadsheets, weighted toward finance where the gap was largest.
InputsInstructions, reference files and an explicit budget (rounds, actions and tokens), shown to the model as it works.
Gold outputsComplete sessions that save a basic but valid file early, then improve it, and end with the file finished inside the budget.
Expert annotationsMarks on which steps were essential versus optional, and a requirement checklist for the final file.
Negative / repair pairsSessions that ran out of budget without a file, paired with a repaired session that delivers. Our 62 cut-off runs are ready-made examples of the failure.
Use as an evaluationHold out a set of tasks as a delivery-under-budget test: report the share of tasks with a valid file at fixed limits, then checklist quality on those files, for each model version and limit setting.
Acceptance testsAutomatic: the file exists, opens and matches the requested format before the session ends. Expert review: core requirements covered.
Proposed sizeA pilot of about 300 tasks with varied budgets, scaled only if the held-out test below improves.
Evidence so far76 of 220 tasks with no usable file; 62 cut off by a limit; 53 of 62 produced a file with more room. On quality: 40 of 143 both-delivered tasks with a checklist item both judges failed for Claude and passed for GPT; 12 draft ledger items (4 quantitative, 3 reference grounding). See Failures.
Other explanationsThe limits may simply be too tight for Claude's style; the retry raised several limits at once; and Claude ran through Databricks, whose serving setup may differ from Anthropic's.
Follow-up testRe-run the 62 tasks raising one limit at a time, and grade the retry files. The dataset is worth building if a simple instruction such as "save a draft early" does not close the gap within the original limits.
